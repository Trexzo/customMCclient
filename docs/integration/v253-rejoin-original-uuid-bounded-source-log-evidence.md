# V253 — Source-scoped genuine original UUID evidence after a real reconnect

V251 consolidated four exact-reference source lease implementations without changing `Minecraft189HostRuntime`, but its first pinned Mojang 1.8.9 original-binary rejoin acceptance run failed while waiting for `CUSTOMMC_189_REJOIN_ORIGINAL_UUID_REVALIDATED_PASS=YES` after the brand-new `CITarget` JVM joined. Existing `wait_for` scanned only `log_tail(host_log)` (last 100,000 bytes). The original Minecraft 1.8.9 client can emit extensive ALSA/LWJGL/OpenAL diagnostics during graphics/audio reconnect. A correct native source witness might be evicted from that moving tail while still present earlier in the log, yielding a false negative. This is a **plausible evidence collection risk, not proof of V251's particular failure cause**: the underlying source-witness may genuinely be absent.

V253 strengthens only the original-binary CI evidence retrieval, **not** native gameplay or the admission gate. Immediately before launching the real new `CITarget` JVM, record the exact host log byte length (`rejoin_host_evidence_offset`). After the dedicated server confirms the second real client join and its teleport, demand `REJOIN_UUID` using the existing `wait_for_new_original_source_marker` helper, which reads ALL original host JVM bytes from that pinned offset to the current end. The helper already enforces process-liveness and the SAME original monotonic `deadline`, requires the unchanged exact native marker and forbids old pre-rejoin evidence. No server-side inference, artificial UUIDs, fixtures, synthetic packets, timeout increase, fallback success or test removal. The existing subsequent B-lock, index reorder, wrong-target veto and controller/damage assertions remain unchanged.

New Python `unittest` tests exercise the actual byte-offset reader against truncated-tails (>100,000 bytes), old-before-offset rejection, fresh-after-offset admission, delayed append, exact marker byte match, stopped original process, invalid boundaries, immutable deadline and unrelated native logs; the official workflow already discovers `test_mojang189_*.py` before the strict pinned Mojang graphical/dedicated-server steps. This change runs the full same original 78-step suite through the existing workflow path trigger.

**Acceptance:** Windows/Ubuntu Foundation, original Mojang 1.8.9 X11 graphical + vanilla server full 78/78 and independent same-SHA rerun.
