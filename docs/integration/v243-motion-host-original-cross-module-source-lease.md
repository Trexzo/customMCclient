# V243 — Native motion host transaction across all Movement modules

Prior V226–V242 hardening pinned many individual module mapped getter/setter stacks. The shared `Minecraft189HostRuntime.playerMotionControl` was NOT pinned. A genuine original `EntityPlayerSP.motionX/Y/Z` getter or setter may synchronously call the host again *while another module still owns that same source player*, allowing a second full Freeze/Flight/Speed/Strafe/ReverseStep/NoGravity/Glide chain and final Criticals motion evidence to run with stale original player and original GUI state. Module-level guards don't cover OTHER modules. This is a genuine ownership boundary rather than a new movement setting.

V243 introduces `Minecraft189MotionHostSourceLease`: one pinned original mapped motion player and initial real ClickGUI focus state across the ENTIRE host motion chain. An unchanged-player reentry is not another tick. A different original player (including null) or a newly focused real GUI irrevocably invalidates the outer chain until it unwinds. The host checks ownership after each individual movement module before entering the next one, and before final original Y/Criticals evidence. A stale player cannot flow through later movement owners after a mapped setter reentry. The host may already have performed a legitimate original native X or Y write before the reentry; no fake rollback. `try/finally` releases the lease even when original mapped getter/setter throws. A fresh subsequent real game callback is admitted normally, with a new original player or GUI policy.

This preserves per-module precedence (Freeze, jump movement, MovementSpeed/AirSpeed, Flight, TargetStrafe, Strafe, vertical owners and DamageBoost), disabled module defaults, no synthetic player input, and all real original source-gate checks. The current focus check treats GUI already open at entry as its original state, not as a new focus loss.

18 new Java 8/JUnit source adapter tests include lease acquisition, nested same/different/null original players, focus transitions, irreversible cancellation, fresh new owner and mapped native setter exceptions. Six of those exercise actual `Minecraft189HostRuntime.install`, real feature catalog and module precedence, mapping original-shaped X/Z/Y getter and setter callbacks back into the host. Both OS Foundation, genuine pinned Mojang Minecraft 1.8.9 graphical X11+vanilla dedicated-server 78/78 and independent unchanged-SHA full native repeat remain mandatory. The unit tests are **not** genuine binary acceptance; production source and original tests must pass on exact V243 SHA. This is a cross-module Movement host integration change; coordinate through Issue #537, preserve other lanes, all PRs Draft, main unchanged.
## Explicit setter-level veto following a nested source change

The initial host-wide checkpoints by themselves were insufficient: a nested original-player callback occurring INSIDE MovementSpeed's mapped X setter could still let that SAME module write its subsequent native Z before returning to the host. The V243 integrated regression caught exactly this (the first candidate's both-OS Foundation FAILED its new test: expected no stale original Z setter, observed one). Corrected production wraps the one original player in a `Minecraft189PlayerMotionControl` guard that delegates all real native X/Y/Z getters, but authorizes **each actual setter individually** only if the same host lease and live GUI focus are still valid. A legitimate first X write is never undone; later Y/Z writes are skipped after player replacement or focus revocation. The final genuine motionY/Criticals witness is likewise revalidated AFTER its native getter returns, to avoid publishing a stale source. The nested getter itself returns genuine values, never invented coordinates. This preserves the existing module-level native guards and older tests. Seven additional adapter regressions cover each setter, getter callback, focus revocation, null source and genuine original setter exceptions.
