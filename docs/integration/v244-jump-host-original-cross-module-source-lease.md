# V244 — One original jump host lease across distinct native jump modules

Original Minecraft189HostRuntime.playerJumpControl dispatched JumpReset, LongJump, HighJump, LowHop, BunnyHop, AutoJump and AirJump in priority order. Individual modules guarded recursive calls from their OWN mapped `EntityPlayer.jump()` source, but there was no shared ownership across the WHOLE host callback. A mapped jump in one module can synchronously dispatch the host again and trigger a different module's pending jump edge before the original call returns, or dispatch with a replacement player while the older module remains in flight.

V244 pins one `Minecraft189PlayerJumpControl` and initial actual ClickGUI focus for the whole host jump chain. Nested same-source host calls are not another real tick; changed original player, null nested source, or newly focused GUI irreversibly revoke further jump authorization. The wrapper delegates `customMcJump()` only while the exact original host lease remains owned. Six checkpoints separate JumpReset, LongJump, HighJump, LowHop, BunnyHop, AutoJump and AirJump. A source setter that changes actual vertical motion then throws is propagated without rollback, and try/finally releases host ownership for a later genuine callback. JumpReset's existing null-source clear behavior remains intact on an ordinary outer null callback, and all per-module priority/activation/settings remain unchanged.

This fix affects common Movement **host routing** only. It does not change Combat JumpReset production logic, jump cadence internals, or native transformers. It cannot prove every possible reentrant read source or guarantee stale module-internal pending boosts are cleared after a world change; these require their own source-specific evidence. Offline Java 8/JUnit source and host integration tests are not pinned Mojang gameplay proof. Require both-OS Foundation, 78-step genuine pinned Minecraft 1.8.9 X11 GUI + vanilla server native acceptance and independent unchanged-SHA original rerun.
