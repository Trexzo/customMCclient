## Java source defect
`Minecraft189WTapModule` sends a real mapped `EntityPlayer.setSprinting(false)` via `Minecraft189PlayerSprintControl`, to begin a synthetic 1–5 callback reset window on a real player sprint/attack source. Existing `writeOriginalSprintReset` exception handling already prevents replay after a partially applied native failure. But an actual original setter may synchronously reenter module disable→enable, suspend for ClickGUI, or change persisted WTap cooldown, reset duration, proximity/forward/sneak/ground and release policy. Previously the initial `apply()` unconditionally scheduled `cooldownRemaining` and `resetTicksRemaining` **AFTER** that external native setter returned. Thus an old original callback could bank a reset window in a NEW activation, or resurrect old GUI policy. During an already active multi-tick reset, a reentrant onDisable could similarly leave the call claiming success for a now-invalid source owner. This is a source-lifecycle correctness gap, not an observed native crash claim.

## V207 actual code
- Monotonic `nativeSprintWriteEpoch` increments on every module `onEnable`, `onDisable`, and `suspendForGui`.
- Immediately before each genuine original `customMcSetSprinting(false)`, capture that epoch and an immutable `NativeSprintPolicy` containing all nine actual persisted admission/cadence values: Require Ground, Require Forward, Pause Sneaking, Require Nearby Player, Cancel Reset on Release, Cooldown, Reset Ticks, Minimum Release Ticks and Max Player Distance (exact finite IEEE-754 comparison).
- After real original mapped setter returns, permit scheduling the next reset ticks or accepting continuation **only if** original module remains enabled, its epoch is unchanged and the nine persisted policy values are still identical. Otherwise clear pending synthetic reset/cooldown and preserve the actual already-held physical left-button edge, preventing stale action replay. A genuine old sprint setter may already have executed; V207 does **not** falsely undo a real native sprint update nor claim that a policy edit never happened if it was edited and restored synchronously to the same value.
- On valid first native setter, use the original captured cooldown/reset duration; no policy variation can be injected between the setter and timer commitment. Retain default one-tick reset, bounded original multi-tick behavior, physical attack edge, validated original sprint/movement/target state, Sneak/Forward/Ground options, and existing catch/finally native setter error safety.
