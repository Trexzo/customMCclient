# V249 — One original world owner across LOS, UUID and entity XYZ reads

The original `Minecraft189HostRuntime.worldEntityPositions` reads native loaded-entity visibility, UUID identity and XYZ triples from separate mapped getters. A getter can synchronously reenter the host with another `World`/loadedEntityList (or null during unload) while a prior sample is being read. Without a common owner, old-world positions may be published next to new-world identity or visibility evidence, potentially changing target decisions.

V249 uses a single `Minecraft189WorldEntityHostSourceLease` across all original visibility, UUID and position getters. A same-world nested callback is not an additional world tick. Another original world (including null) irrevocably revokes the outer source before any other source data can be published. The host checks source identity after every mapped getter; on revocation, original position/UUID/visibility, combat and target-selection evidence is cleared, including remembered KillAura UUID target and transient original-world handles. The existing optional visibility and UUID policies, including their deliberate RuntimeException fail-closed behavior and independent feature admission, remain intact. Invalid packed XYZ and genuinely throwing position getters clear all partially collected source evidence; native exceptions remain observable. An actual next host callback after the first stack unwinds can accept the new world.

This is host integration source protection, not a new Combat targeting policy or a guarantee that the *contents* of an unchanged Java World cannot reorder mid-read. Separate list-generation proof would be needed for that case. No Combat/Render module production files are modified. Java 8 JUnit native-shaped source and HostRuntime integration tests are offline evidence; they do not replace exact pinned genuine Minecraft 1.8.9 X11 graphical plus vanilla server 78-step admission or independent unchanged-SHA rerun.
