## Production-original source loophole
`Minecraft189HostRuntime.shouldAutoClick()` (dedicated TriggerBot branch) certifies actual current `WorldClient.loadedEntityList` original UUIDs and target index, accumulates CPS/confirmation credit in `TriggerBot`, and returns a boolean to `Minecraft189RuntimeBridge`. The latter may execute mapped source Inventory/currentItem getters/setters, AutoBlock release and KeepSprint before the real original `PlayerControllerMP.attackEntity`. Previously its TriggerBot dispatch branch then read the **CURRENT** `worldEntityUuidState.snapshot().at(playerIndex)` and passed this NEW UUID into `triggerDispatchUuid` as if it were the same UUID that earned credit. If the original loaded list index was recycled or swapped (A→B→A) between admission and actual dispatch, same numerical playerIndex could authorize another player without new TriggerBot confirmation, even though final native controller ensured consistency with the **newly** supplied UUID. This is a static Java source owner gap, not proof a native-game exploit or server packet was observed.

## V204 actual source fix
- Introduce `Minecraft189TriggerDispatchUuidLease`: a one-shot scheduled **actual native source UUID + TriggerBot module epoch** authorization. Null/mismatch/disabled/GUI or different epoch consume it without a packet and never allow reuse.
- In `HostRuntime.shouldAutoClick`, clear old dispatch authorization on each new scheduler callback and increment a reentrant admission serial. A nested original mapped callback cannot let its outer, stale scheduler re-arm an old target after a newer decision.
- When TriggerBot actually earns a click via V203's source UUID getter ticket and `shouldClick()`, retain that **exact verified native UUID** and its current module epoch. All ordinary original antibot/friend/wall/Range/HitSelect/Criticals gates must also approve; immediately before returning true, assert this is still the same scheduler generation/module activation and same source native player UUID index. Only then arm the one-shot UUID.
- At actual RuntimeBridge synthetic melee dispatch, after native currentItem/slot/source ownership verification and source `WorldEntityUuidState.at(playerIndex)` lookup but **BEFORE** `customMcAttackCrosshairEntity()`, consume the expected original UUID and epoch. Any recycled index A→B or OFF→ON is a **no-action veto**, not a passing hit, and the already existing native ray/controller `triggerDispatchUuid` and positive vanilla dedicated-server damage requirements remain independently intact.
- Move `syntheticTriggerStarted` original acceptance record to after successful UUID source lease consumption; a rejected transient UUID change must not issue an artificial trigger-start success. Original native controller hook and UUID/raycast checks remain unchanged.
- Re-sample actual physical left/right pointer after V203's external mapped World UUID getter; changes during native read use real current manual-input eligibility.
- Manual genuine mouse clicks, non-TriggerBot AutoClicker and KillAura are unaffected. No fake source World, UUID, player, packet, held slot, camera or attackEntity argument.
