# V217 — original Target HUD must not mix two different player World/rotation snapshots

## Actual production UI correctness gap
`Minecraft189TargetHudModule.TargetHudPass.render` reads one `Minecraft189NearestPlayerTargetState.Snapshot` (original source player index/coordinates/distance) and one `Minecraft189TargetRotationState.Snapshot` (yaw/pitch derived from the original earlier selected target). Previously it displayed a Target HUD card whenever **each** snapshot was individually available. On an actual World/player rejoin, A→B target switch, or updated source position before the next rotation recomputation, the latest source target could already be player B/distance=8, while the independently stored rotation still belonged to player A/distance=5. The card then presented **B's index/distance with A's yaw/pitch**, a misleading unsupported combination. This is a Java production render snapshot consistency issue, not an observed original client crash or packet-level spoofing.

## V217 source correction
- Add `Minecraft189TargetHudModule.matchingSourceTarget(target, rotation)`, which requires both snapshots nonnull and available, a found genuine source target, the **same exact selected original entity index** and the **same finite nonnegative source distanceSquared** that the rotation calculation copied from its target snapshot. Preserve legitimate zero source distance if rotation was actually available, and exact floating-point (including signed zero) snapshot comparison.
- In the existing render pass, **draw nothing** unless that congruence holds. No interpolated new yaw, no stale old distance card, no invented target or UUID, and no replacement of actual native PvP controller, current GUI, raytrace, identity or 3D distance admission.
- A new genuine World target followed by recalculating `Minecraft189TargetRotationState` makes the card visible again. Existing stable target HUD visual layout, compact and full geometry, X/Y settings, optional Proximity Meter/adaptive color, optional source coordinates, and original render-pass cleanup remain unchanged.
- This is **display-only source congruence**, not a full UUID/World freshness claim: a recycled index at the same distance cannot be distinguished without a native UUID in these two snapshots. The genuine downstream combat UUID validation remains independent and unchanged.
